# PIG e-ADMIN 1.0

Електронна административна система за **ПИГ „Св. Климент Охридски“** — централизирано
управление на кандидатстването, подбора на персонал, акредитацията, документооборота и
институционалния контрол.

> **Една институция. Единна система. Пълен контрол.**

Това не е презентационен сайт, а работеща административна система: реална база данни,
профили с роли и права, електронни формуляри, документооборот с версии, комисии с
поверителни оценки, одиторски журнал и автоматизации.

## 2. Бърз старт (без външни услуги)

Изисквания: **Node.js 20+**, npm.

```bash
npm install
cp .env.example .env.local     # по избор — може и без него
npm run dev
```

Отворете <http://localhost:3000>.

Без зададени ключове за Supabase системата стартира в **локален режим**: данните се пазят
в `./.data/db.json`, а файловете — в `./.data/uploads`. Всички функции работят, което
позволява пълна демонстрация и разработка офлайн.

**Профил по подразбиране (само локален режим):**

| Имейл | Парола | Роля |
| --- | --- | --- |
| `admin@pig-ohridski.bg` | `Admin123!` | Суперадминистратор |

> Сменете паролата веднага: **Настройки → Профил**, или задайте свои стойности чрез
> `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` **преди** първото стартиране
> (след като `.data/db.json` е създаден, тези променливи вече не се използват).

Полезни команди:

```bash
npm run dev          # разработка
npm run build        # продукционен билд
npm run start        # стартиране на билда
npm run test         # unit тестове (Vitest)
npm run test:e2e     # E2E с реален браузър (изисква изграден билд)
npm run create-admin # създаване на административен профил
```

## 3. Режими на работа

| Режим | Кога се активира | Съхранение | Употреба |
| --- | --- | --- | --- |
| **Supabase** | зададени `NEXT_PUBLIC_SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` | PostgreSQL + Supabase Storage | продукция |
| **Firebase** | зададен `NEXT_PUBLIC_FIREBASE_DATABASE_URL` (има и стойност по подразбиране) | Firebase Realtime Database + файлове като base64 възли | продукция без Supabase, демо на живо |
| **Локален** | `DATA_MODE=local` или липсват всички ключове | `./.data/db.json` + `./.data/uploads` | разработка, тестове |

Изборът е автоматичен (`lib/db/index.ts`), а интерфейсът е един и същ. Таблото показва
дискретен банер, че данните не са в реална база, когато режимът е локален.

### Firebase режим — как работи

- Данните живеят в `/tables/<таблица>/<id>` на Realtime Database през REST API
  (`lib/db/firebase.ts`), без Admin SDK и без service account.
- Прикачените файлове се качват в `/_files/<ключ>` на части по 2 MB (base64), защото
  Storage не е активиран в проекта. Затова качените документи оцеляват при рестарт.
- При първи достъп базата се зарежда сама (`lib/db/seed-firebase.ts`): настройки на
  институцията, bootstrap администратор и защитеният суперадминистратор.
- RTDB не пази `null` стойности и не допуска `. # $ [ ]` в имената на възли — кодът
  работи с `!= null` проверки и нормализира файловите ключове.

> ⚠️ **Сигурност:** правилата на RTDB в момента са отворени, защото приложението няма
> Firebase Auth. Всеки, който знае адреса на базата, може да чете и пише. За реална
> експлоатация или преминете към Supabase (с RLS), или включете Firebase Auth и
> затворете правилата. Демо публикацията е подходяща за преглед, не за лични данни.

> Локалният режим **не е подходящ за Vercel** — файловата система там е само за четене.

| `RESEND_FROM` | не | Подател, напр. `PIG e-ADMIN <no-reply@pig-ohridski.bg>` |

> Системата **не твърди, че дадена интеграция работи**, ако няма ключ. Статусът се вижда в
> **Настройки → Системен статус** (режим на данни, Resend, 2FA, брой записи).

## 5. Supabase: база, миграции, RLS

1. Създайте проект в <https://supabase.com>.
2. От **Project Settings → API** копирайте `URL`, `anon key` и `service_role key`.
3. Изпълнете SQL скриптовете **в този ред** (SQL Editor или `supabase db push`):

```text
database/migrations/0001_schema.sql   -- типове, таблици, индекси, ограничения, тригери
database/migrations/0002_rls.sql      -- помощни функции, RLS политики, anti-escalation тригери
database/migrations/0003_protected_superadmin.sql  -- защитен профил на собственика
database/migrations/0004_invoices.sql -- фактури, редове и контрагенти + права
database/seed.sql                     -- роли, права, системни настройки
```

4. **Storage**: скриптът `0002_rls.sql` създава private bucket `candidate-documents`
   (10 MB, само PDF/JPG/PNG) и политиките към него. Ако bucket-ът вече съществува,
   проверете дали е **private**.
5. Попълнете `.env.local` (или променливите във Vercel) и рестартирайте.

### Схема на данните (основни таблици)

`users`, `profiles`, `roles`, `permissions`, `role_permissions`, `user_roles`,
`job_posts`, `applications`, `candidate_documents`, `application_events`, `committees`,
`committee_members`, `evaluation_criteria`, `evaluations`, `accreditation_cycles`,
`criteria`, `evidence`, `institutional_reports`, `documents`, `document_versions`,
`tasks`, `notifications`, `audit_logs`, `system_settings`, `invoice_clients`, `invoices`,
`invoice_items`.

Всички ключове са UUID, връзките са с външни ключове и индекси, а за бизнес правилата има
`CHECK` ограничения (напр. размер на файл 1 B – 10 MB, уникален код на критерий в рамките
на цикъл, една роля от даден вид на потребител).

### RLS (Row Level Security)

- Публично се четат само **публикувани** обяви.
- Анонимен кандидат може да **вмъкне** кандидатура само със статус `submitted` и без
  комисия/оценка — не може да чете чужди кандидатури.
- Кандидатът чете собствените си кандидатури по имейл.
- Оценките (`evaluations`) са достъпни само за членове на съответната комисия, директора и
  суперадминистратора.
- Документите, задачите и известията са достъпни само за служебни профили с нужното право.
- Тригерите `guard_user_update` и `guard_user_roles` **забраняват** потребител да си
  повишава ролята или да се самоактивира/деактивира през API.

## 6. Първи администратор

### Supabase режим

```bash
npm run create-admin -- \
  --email=director@pig-ohridski.bg \
  --password='СилнаПарола123' \
  --name='Радослав Якимов' \
  --position='Директор' \
  --role=director
```

Скриптът създава потребител в Supabase Auth, запис в `public.users` и роля в
`public.user_roles`. Паролата се проверява от Supabase Auth (`password_hash` остава `NULL`).

### Локален режим

```bash
npm run dev            # веднъж, за да се създаде ./.data/db.json
npm run create-admin -- --email=admin@pig-ohridski.bg --password='Admin123!' --role=superadmin
```

Позволени роли: `superadmin`, `director`, `deputy_director`, `accreditation_expert`,
`hr_expert`, `committee_chair`, `committee_member`, `ict_officer`, `teacher`.

> Профил с роля `superadmin` не е член на институцията и не се брои в списъците с персонал.

### Защитен суперадминистратор (собственик на системата)

Профилът на собственика се създава автоматично от променливите:

```env
PROTECTED_SUPERADMIN_EMAIL="atodorov434@gmail.com"
PROTECTED_SUPERADMIN_PASSWORD="…"
PROTECTED_SUPERADMIN_NAME="Алекс Тодоров"
PROTECTED_SUPERADMIN_POSITION="ИКТ специалист"
```

В локален режим проверката се изпълнява **веднъж на процес** при първия достъп до
файловата база. Така профилът се възстановява и след рестарт на средата или при
ефимерна файлова система (демо публикация), когато `./.data/db.json` се пресъздаде.

Профилът е със `is_protected = true` и:

| Действие | Резултат |
|---|---|
| Изтриване | не е възможно (няма такова действие в интерфейса) |
| Деактивиране | блокирано в интерфейса и в сървъра (`assertNotProtected`) |
| Понижаване на ролята | блокирано в интерфейса и в сървъра |
| Смяна на паролата от друг | само друг `superadmin` |
| Създаване на нови администратори | разрешено (`staff.manage`) |

В Supabase режим същото се пази и на ниво база — `database/migrations/0003_protected_superadmin.sql`
(колона `is_protected` + тригер, който отказва `delete`, `is_active = false` и смяна на ролята).

## 7. Имейл известия (Resend)

1. Регистрация в <https://resend.com>, добавяне и верификация на домейн.
2. `RESEND_API_KEY` и `RESEND_FROM` в средата.
3. Проверка: **Настройки → Системен статус** показва дали имейлите са активни.

Без ключ системата записва известията в базата и отбелязва `email_status = 'skipped'` —
това е видимо в **Известия**, така че липсата на интеграция е явна, а не прикрита.

Автоматично се изпращат: потвърждение при подадена кандидатура, промяна на статус,
нова задача, резултат от решение, напомняния за срокове (cron).

## 8. Деплой във Vercel

```bash
npm i -g vercel
vercel link
vercel env add NEXT_PUBLIC_SUPABASE_URL production
vercel env add NEXT_PUBLIC_SUPABASE_ANON_KEY production
vercel env add SUPABASE_SERVICE_ROLE_KEY production
vercel env add AUTH_SECRET production
vercel env add NEXT_PUBLIC_APP_URL production
vercel env add CRON_SECRET production
vercel --prod
```

- `vercel.json` съдържа cron задача `0 7 * * *` към `/api/cron/reminders`.
- След деплой задайте `NEXT_PUBLIC_APP_URL` на реалния домейн (иначе линковете в имейлите
  сочат към `localhost`).
- `AUTH_SECRET` трябва да е различен за всяка среда; смяната му прекратява всички сесии.
- Не качвайте `.env.local` в git (налично в `.gitignore`).

### Модул „Фактури“ (`/dashboard/invoices`)

Издаване на фактури, проформа фактури, дебитни и кредитни известия и сторно — по модела на
invoice.bg, но изцяло в системата (без външна услуга).

- **Жизнен цикъл**: `чернова → издадена → платена`, плюс `анулирана`. Черновата се редактира
  и трие; **издаденият документ е заключен** — корекции се правят с кредитно известие или
  сторно, свързани с първичния документ (`related_invoice_id`).
- **Номерация**: непрекъсната серия за всеки вид — фактурите са 10 цифри (`0000000001`),
  останалите с префикс `ПРО-`, `ДИ-`, `КИ-`, `СТ-` (`lib/numbering.ts`).
- **Суми**: редове „количество × единична цена“, ДДС по ставката на реда (20 / 9 / 0 %),
  разбивка по ставки в печатния вид (чл. 114 ЗДДС), закръгляване до стотинка и
  **сума словом** на български (`lib/invoices.ts`).
- **Контрагенти** (`/dashboard/invoices/clients`): данните се копират като **снимка** в
  документа при издаване, така че по-късна промяна не променя вече издаден документ.
  Контрагент с документи в регистъра не се трие.
- **Плащания**: цялостно или частично; остатък и „просрочена“ се смятат автоматично.
  Кредитните известия и сторното не са вземания — не влизат в „неплатени“ и не се плащат.
- **Печат/PDF**: `A4` лист с издател, получател, редове, ДДС разбивка, сума словом, подписи;
  воден знак „Анулирана“; данните на издателя идват от
  „Настройки → Данни за фактуриране“ (`invoice_supplier_*`, `invoice_due_days`,
  `invoice_footer_note`).
- **Права**: `invoices.view` / `invoices.manage` (суперадминистратор, директор,
  зам.-директор); всяко действие се записва в одиторския журнал (`invoice.*`).

## 10. Роли и права (RBAC)

Единен източник на истина: `lib/permissions/roles.ts` (огледален в `database/seed.sql`).

| Роля | Ключови права |
| --- | --- |
| `superadmin` | Всичко, включително настройки и одитен журнал; не е член на институцията |
| `director` | Пълен институционален контрол + окончателни решения (`director.decide`) |
| `deputy_director` | Като директор без окончателното решение |
| `accreditation_expert` | Акредитация, качество, документи, анализи |
| `hr_expert` | Обяви, кандидатури, персонал (без окончателно решение) |
| `committee_chair` / `committee_member` | Поверителни оценки по възложени кандидатури |
| `ict_officer` | Технически настройки — **без** достъп до кадрови досиета и оценки |
| `teacher` | Собствен профил, задачи, известия |
| `candidate` | Само собствени кандидатури (`/track`) |

Правила, наложени и в интерфейса, и в сървъра, и в базата:

- **Един човек може да има няколко роли** (напр. `deputy_director` + `committee_chair`).
  Правата са **обединение** на всички негови роли; в регистъра и в хедъра се показват
  всички роли. Ролите се задават с отметки при създаване и в
  `/dashboard/staff/[id]` → „Роли и достъп“ (замества целия набор).
- Никой не може да промени **собствените си** роли или да се активира/деактивира.
- Само `superadmin` управлява други суперадминистратори.
- Окончателно решение по кандидатура — само с право `director.decide`.
- Фактури се издават само с `invoices.manage`; прегледът на регистъра иска `invoices.view`.
- Член на комисия не може да оценява при деклариран конфликт на интереси.

## 11. Сигурност

- **Автентикация**: scrypt хеширане (`scrypt$N$salt$hash`), HMAC-подписани сесийни
  бисквитки (8 часа, `HttpOnly`, `SameSite=Lax`), опция за Supabase Auth.
- **2FA (TOTP)**: RFC 4226/6238, QR код, потвърждение и изключване с повторна парола.
- **Защита от brute force**: ограничение 6 опита / 10 мин. на имейл+IP и блокиране на
  профил за 15 мин. след 8 неуспешни опита; еднакво време за отговор при липсващ профил.
- **Валидация**: Zod за всеки формуляр; файлове — разширение + MIME + размер (≤ 10 MB).
- **Качване**: private bucket / локална папка; имената се нормализират; защита срещу
  path traversal при сваляне; достъпът минава през проверка на права.
- **Одиторски журнал**: вход, изход, промени по статуси, документи, роли, настройки,
  експорти — с автор, време, IP и потребителски агент.
- **Изтриване на профили**: необратимо, но обградено с проверки — не може собствен профил,
  защитен профил (собственик/суперадминистратор), последният суперадминистратор и профил
  с вписани оценки в комисия (пази протокола). Заедно с профила се махат ролята,
  членството в комисии, личните данни и известията; журналът остава.
- **HTTP**: HTTPS/HSTS, `X-Frame-Options: SAMEORIGIN`, `nosniff`, `Referrer-Policy`,
  `Permissions-Policy`; `noindex` за панела и печатните изгледи.
- **Секрети**: service role ключът се използва само на сървъра; `.env*` е извън git.

## 12. Лични данни и срокове за съхранение

- Обработване съгласно Регламент (ЕС) 2016/679; публичната политика е на `/privacy`.
- Срокове по подразбиране (`system_settings.retention_months`, по подразбиране 60 месеца):
  неодобрени кандидатури — до 6 месеца след приключване на процедурата; одиторски журнал —
  24 месеца; служебни документи — съгласно номенклатурата.
- Индивидуалните оценки на комисията **не се показват** на кандидата; той вижда етап,
  краен резултат и мотиви.
- Изтриването на кандидатура е архивиране (`status = archived`) — физическото изтриване се
  извършва административно след изтичане на срока, за да се запази одитната следа.

## 13. Архив, резервни копия и възстановяване

**Supabase**: включете автоматичните Daily backups (Plan → Database → Backups) и
периодично сваляйте `pg_dump` извън доставчика.

```bash
pg_dump "$SUPABASE_DB_URL" --no-owner --no-privileges -f backup-$(date +%F).sql
```

Файловете от bucket `candidate-documents` се архивират отделно (`supabase storage cp`).

**Локален режим**: копирайте `./.data` (съдържа `db.json` и `uploads/`).

**Възстановяване**: нов проект → `psql < backup.sql` → възстановяване на bucket → нови
`SUPABASE_*` ключове → рестарт. Сесиите се прекратяват (нов `AUTH_SECRET` е допустим).

Препоръчителна проверка веднъж месечно: вход с тестов профил, създаване на чернова,
качване на файл, експорт на DOCX, преглед на одиторския журнал.

## 15. Тестове

```bash
npm run test        # 66 unit теста
npm run build && npm run test:e2e   # 32 E2E проверки в реален Chrome
```

**Unit** (`tests/unit/`): хеширане и подписване, TOTP срещу официалните RFC вектори,
матрица на правата (вкл. че ИКТ няма достъп до кадри и оценки), Zod схеми, файлова
валидация и защита от path traversal, навигация по права, помощни функции, фактурни
изчисления (закръгляване, ДДС по ставки, сума словом, вземания/просрочие).

**E2E** (`tests/e2e.mjs`, puppeteer-core + Chrome): начална страница → вход → създаване и
публикуване на обява → публичен детайл → кандидатстване с качване на PDF → регистрационен
номер → проследяване (и отказ при грешен имейл) → кандидатурата в регистъра → анализи →
одитен журнал → мобилна ширина без хоризонтален скрол → светла тема → защитени маршрути и
файлове.

Скриптът сам стартира `next start` на порт `3210` с отделна база (`.data-e2e`) и прави
снимки в `tests/screenshots/`.

**Защитен суперадминистратор** (`tests/superadmin-check.mjs`): вход с профила на собственика,
маркер „заключен профил“, липса на бутон „Управление“ за него, създаване на втори
администратор от него, вход с новия профил, отказ при грешна парола.

```bash
BASE_URL="http://127.0.0.1:3300" node tests/superadmin-check.mjs
```

**Firebase режим** (`tests/firebase-flow.mjs`): обява → публикуване → кандидатстване с PDF →
файлът се записва в RTDB и се сваля обратно → данните се проверяват директно в базата.
Тестът работи с реалната база и изчиства създаденото след себе си.


**Изтриване на профили** (`tests/delete-staff.mjs`): създава служител, отваря страницата

```bash

```

**Множествени роли** (`tests/multi-role.mjs`): създава служител с две роли от регистъра,

```bash

```

**Модул „Фактури“** (`tests/invoices.mjs`): самостоятелен сценарий (стартира `next start`

## 17. Ограничения на първата версия

- **PDF** се генерира чрез печатния изглед на браузъра (`/print/...`), а не чрез сървърен
  PDF двигател — така няма тежка зависимост, но изисква „Печат → Запази като PDF“.
- **Акредитацията** е вътрешна система за самооценка и доказателства. Тя **не** представя
  вътрешната оценка като официална държавна акредитация — текстът е изрично указан в
  модула.
- **2FA** е задължителна по политика за административните роли, но не се налага принудително
  от системата при първи вход; потребителят се подканва в „Сигурност“.
- **Локалният режим** е за разработка/демо — при паралелни процеси и при Vercel е нужен
  Supabase.
- **Имейли** изискват Resend и верифициран домейн; без тях известията остават в системата.
- **Фактурите** се издават и печатат в системата; няма връзка с НАП (е-фактуриране,
  подаване на справки) и няма автоматично изпращане по имейл — документът се запазва като
  PDF от печатния изглед.
- Няма интеграция с държавни регистри (НАП, МОН) — предвидена е като следващ етап.
